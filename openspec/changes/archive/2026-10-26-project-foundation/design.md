# Design

## Context

The repository has no application code (see proposal.md - Why). The stack is fixed: Python, FastAPI, PostgreSQL. The frontend is a separate repository and talks to this service only over HTTP/JSON. Later MVP modules (identity, households, budgets, catalog, stores, prices, shopping, optimization) will all plug into what this change establishes, so the structure and conventions chosen here are the main output.

```
  +------------------+        HTTPS / JSON        +---------------------------+
  |  Frontend        |  ----------------------->  |  lumior-be (FastAPI)      |
  |  (separate repo) |  <-----------------------  |   routers -> services     |
  +------------------+   contract: /api/v1 +      |           -> repositories |
                         OpenAPI document         +-------------+-------------+
                                                                |  async SQLAlchemy / asyncpg
                                                                v
                                                  +---------------------------+
                                                  |  PostgreSQL (+ pg_trgm)   |
                                                  +---------------------------+
```

## Goals / Non-Goals

**Goals:**
- A layout where each business module is self-contained and the layering rule is clear.
- One way to get config, one way to get a DB session, one error format. No per-module variations.
- Integration tests that run against real PostgreSQL from day one.
- Shared money and unit primitives so later modules never use floats for money or ad-hoc unit strings.

**Non-Goals:**
- Authentication, authorization, and tenancy enforcement (next change: `auth-and-households`).
- Background workers, queues, Redis, or caching.
- Deployment target, container image publishing, and production infrastructure.
- Observability beyond structured logging with a request ID (no metrics or tracing backend yet).

## Decisions

### 1. Modular monolith, one service and one database

Layout:

```
src/lumior/
  main.py          app factory: create_app(settings)
  core/            config, db, errors, logging, money, units
  api/             v1 router aggregation, shared dependencies
  modules/<name>/  models.py, schemas.py, repository.py, service.py, router.py
```

Layering rule: `router -> service -> repository -> models`. Routers handle HTTP and Pydantic schemas only. Services hold business rules and never import FastAPI. Modules talk to each other through services, never through another module's repository or models.

*Alternatives:* microservices (too much operational cost for an MVP with one team); layer-first layout (`routers/`, `models/` at top level) makes module boundaries invisible and harder to split later.

### 2. Async SQLAlchemy 2.x with asyncpg; Alembic for migrations

One `AsyncEngine` per process, one `AsyncSession` per request provided by a FastAPI dependency. The session commits on success and rolls back on error at the request boundary. Services do not commit on their own, so a multi-step operation (for example, "complete trip" later) is one transaction. Relationships default to `lazy="raise"` so accidental lazy loads fail loudly instead of breaking in async code.

Alembic uses the same metadata as the models and a naming convention for constraints so autogenerated migrations are stable. The baseline migration enables `pg_trgm` (needed by product search later) and creates no tables.

*Alternatives:* sync SQLAlchemy (simpler, but blocks the event loop under FastAPI's async handlers); SQLModel (ties DB models and API schemas together, which this design keeps separate); raw asyncpg (no ORM or migration tooling).

### 3. Configuration via pydantic-settings

A single `Settings` object loaded from environment variables (and `.env` in local dev): `ENVIRONMENT`, `DATABASE_URL`, `CORS_ALLOWED_ORIGINS`, `LOG_LEVEL`, and a `SECRET_KEY` placeholder for the auth change. It is validated at startup, so a missing value fails fast. The app factory takes `Settings` as an argument, which lets tests build an app with test settings.

### 4. API conventions

- All business routes mount under `/api/v1`. Health endpoints live at the root (`/health/live`, `/health/ready`) so infrastructure probes do not depend on API versioning.
- One error envelope for every non-2xx response, including validation errors and unhandled exceptions:

  ```json
  { "error": { "code": "validation_error", "message": "...", "details": [...], "request_id": "..." } }
  ```

  Domain code raises typed exceptions (`NotFoundError`, `ConflictError`, ...) defined in `core/errors`. Exception handlers map them to status codes and the envelope. Unhandled exceptions return a generic 500 without internal details.
- Every response carries an `X-Request-ID` header (echoed from the request or generated). The same ID appears in logs and error bodies.
- CORS allows only origins from `CORS_ALLOWED_ORIGINS`. No wildcard when credentials are allowed, which keeps cookie-based refresh tokens possible if the frontend turns out to be web.
- OpenAPI is served at `/api/v1/openapi.json`, with docs UI enabled outside production. Stable `operationId`s (`<module>_<action>`) make generated frontend clients readable.

*Alternative:* RFC 7807 `application/problem+json`. It is a reasonable standard, but a single custom envelope with a stable `code` field is simpler for the frontend to handle. Switching later is possible because all errors go through one handler.

### 5. Money and units as shared primitives

- `core/money`: amounts are `Decimal`, stored as `NUMERIC(14,2)`, and serialized as strings in JSON so clients never parse them into floats. A `Money` value pairs an amount with an ISO 4217 currency code. Rounding (half-up) is defined once here. Currency precision comes from a lookup table, so the target currency does not need to be decided in this change.
- `core/units`: a small fixed set of base units (`g`, `ml`, `piece`) with conversions from common units (`kg`, `l`, ...). Later the catalog stores product size in a base unit, which makes per-unit price comparison possible.

*Alternatives:* integer minor units (also safe, but awkward for currencies like IDR where amounts are shown without decimals and for unit-price math); a units library like `pint` (heavy for three base units).

### 6. Tooling

- Python 3.12, dependencies and lockfile managed by `uv`.
- `docker-compose.yml` with PostgreSQL 16 for local development.
- `ruff` (lint + format), `mypy` in strict mode for `src/`.
- `pytest` with two levels: `tests/unit` (no I/O) and `tests/integration` (testcontainers PostgreSQL, migrations applied once per session, each test wrapped in a rolled-back transaction).
- CI runs lint, type check, and both test levels on every push and pull request.

## Risks / Trade-offs

- [Async SQLAlchemy pitfalls such as lazy loading and session misuse across tasks] → `lazy="raise"` default, a session per request only, explicit `selectinload` in repositories.
- [Module boundaries erode as features grow] → layering rule documented in the README. Optionally add an import-linter contract in CI later.
- [Testcontainers needs Docker in CI and on developer machines] → it's already needed for docker-compose. CI uses a runner with Docker available.
- [The custom error envelope differs from RFC 7807] → errors are centralized in one handler, so changing format later is contained.
- [The `NUMERIC(14,2)` scale may not fit every currency] → the scale is defined in one place. Revisit when the target market is fixed. 2 decimals already covers IDR and most major currencies.

## Migration Plan

No existing system or data. Rollout is: merge the skeleton, apply the baseline migration on each environment's database, and point the health probes at `/health/live` and `/health/ready`. Rollback is reverting the commit. The baseline migration only enables an extension.

## Open Questions

- Target region/currency: affects seed data and default currency in later changes. It does not change this design because currency precision is table-driven.
- Frontend type (web, mobile, or both): affects token transport in `auth-and-households`. This change keeps CORS compatible with both.
- Deployment target (for example Fly.io, Render, or a VPS): affects packaging in a later change, not the application structure.
